# Fly-Lang 沙箱安全白皮书

> 状态：提案 / 待评审（两轮设计迭代已收敛）
> 目标读者：项目维护者、安全审计方
> 配套文档：[THREAT-MODEL.md](./THREAT-MODEL.md)（编译期 + 进程内运行时威胁模型）、[Rust迁移方案.md](./Rust迁移方案.md)
> 原则：**诚实披露边界**——能保证什么、不能保证什么、为什么，全部写清；接受矛盾，不掩盖矛盾

## 1. 设计目标

1. **编译即安全**：利用 Fly-lang 的 8 个安全关键字，在编译期消灭绝大多数漏洞
2. **运行时隔离**：将不可信代码放入轻量级进程沙箱，限制系统资源与能力
3. **核心逻辑可证明**：沙箱最关键的资源记账组件经过建模/测试双重验证，终止判定逻辑经形式化证明
4. **部署环境稳固**：沙箱运行在最小化、一次性的隔离环境中，杜绝持久化攻击
5. **性能可接受**：快速模式启动延迟 < 30ms，内存开销 < 20MB

### 1.1 与现有沙箱的关系（继承而非推倒）

现有沙箱（THREAT-MODEL.md）是**编译期关键字拦截 + 进程内 `_FlySandbox` 代理**。本方案在其上增加**进程级隔离层**，两者纵深叠加：

| 层 | 现有（已发布） | 本方案新增 |
| :--- | :--- | :--- |
| 编译期 | 8 关键字静态检查（E0063-E0066 等） | 污点追踪强化（input()/网络读取 → safe 前必须清洗） |
| 进程内 | `_FlySandbox`/`_FlyOnly` 运行时代理 | 保留，作第二道防线（纵深防御） |
| 进程级 | 无 | `fly-sandboxd`：命名空间 + seccomp + cgroups |
| 部署 | 无 | 一次性容器/微VM（安全模式，可选） |

## 3. 双模式执行（矛盾一的解决方案）

> 性能目标（<50ms）与容器冷启动（100-300ms）在底层路径上矛盾——fork+exec 与容器运行时规范是两个量级。**不掩盖矛盾：拆为两档 SLA，透明降级。**

| 模式 | 启动延迟 | 隔离强度 | 实现方式 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **快速模式 (Fast)** | < 30ms | 进程级（namespaces + seccomp） | `clone(CLONE_NEWNS\|NEWNET\|NEWPID\|...)` + `execve` Python；预热解释器池复用 `libpython` 状态，传 `.pyc` | 高频函数调用、AI 推理辅助、实时插件 |
| **安全模式 (Secure)** | ~150-300ms | 硬件辅助虚拟化 / 容器隔离 | Firecracker 微VM / gVisor sentry，按容器语义执行 | 多租户 SaaS、第三方代码、金融合规 |

**实现细节**：
- 共享同一 `fly-sandboxd`，仅启动路径不同
- 用户显式指定 `fly run --mode=fast|secure`，或调度器按负载/风险自动路由（高并发 → fast，高敏感 → secure）
- 文档明确标注延迟与隔离强度的 trade-off

## 4. 形式化验证策略（矛盾二的解决方案）

> SPARK 写整个权限验证器成本远大于收益（几十行布尔逻辑）。**精准裁剪：只证明最值得证明的组件。**

| 组件 | 验证手段 | 理由 |
| :--- | :--- | :--- |
| 资源记账（配额计算/防超额分配/并发一致性） | **TLA+ 建模 + proptest 状态机测试**（CI 数千次随机并发，对比模拟模型） | 最棘手的并发正确性问题，模型检查收益最高 |
| 终止判定（配额耗尽是否终止） | **SPARK 证明**（唯一数学证明组件，< 30 行，C ABI 静态库，Rust `extern "C"` 调用） | 极简、独立、全沙箱资源超限流程的"总开关" |
| 其余 99%（Python 代理、编译期检查、网络过滤） | 防御性编程 + 运行时断言 + 单元测试 + 混沌测试 | 形式化是"冷兵器"，不适合日常大规模代码 |

**终止判定 SPARK 示例**（SPARK 可证明，Rust 通过 FFI 调用，无 Ada 运行时）：

```ada
-- 判定沙箱是否应终止（由于配额耗尽）
function Should_Terminate(PID : Integer; Used_Mem, Limit_Mem : Unsigned_64) return Boolean
with Pre  => Used_Mem <= Limit_Mem * 2,   -- 避免无意义溢出
     Post => (if Should_Terminate then Used_Mem > Limit_Mem);
```

## 5. 各层详细设计

### 5.1 第一层：编译器增强（Go）

- **污点追踪**：标记 `input()`、网络读取等外部数据为污点；传递给 `safe` 标记函数前必须清洗（类型转换/正则过滤），否则编译报错（新错误码，注册进 internal/ast/errors.go）
- **能力白名单检查**：`only (mods):` 块内所有调用须属于白名单模块（现有 checker 强化）
- **资源配额生成**：`cage(max_time, max_memory)` 生成的 Python 代码插入沙箱配额 RPC 请求（原进程内装饰器保留为 fast 模式兜底）
- **敏感数据流检查**：`mask` 变量赋值路径追踪，禁止流入输出/日志/网络（现有实现强化）

### 5.2 第二层：fly-sandboxd（Rust）

- **隔离**：Mount（只读）、PID、Network（默认无，veth 显式授权）、User（UID 65534）、UTS、IPC 命名空间
- **seccomp-bpf**：白名单约 40 个系统调用（read/write/openat 受限路径/close/exit 等），屏蔽 mount/clone/ptrace 等
- **配额**：cgroups v2（CPU 时间片、内存上限、磁盘 IO）
- **能力令牌**：启动时绑定 `only` 白名单；Python 侧模块调用经 UDS 向代理校验
- **技术栈**：seccomp-rs / cgroups-rs / tokio / nix / serde+bincode（UDS RPC）

**启动流程**：
1. `fly run app.fly` → 编译器生成临时 `.py`
2. `fly` 客户端经 UDS 向 `fly-sandboxd` 发启动请求（配额、白名单、代码路径）
3. `fly-sandboxd` 按模式路由：Fast → `clone(...)` + seccomp + `execve python3`；Secure → Firecracker/gVisor
4. Python 运行，对外调用经预置 `sandbox` 模块向代理查询权限

### 5.3 第三层：核心安全内核

- 权限验证器：白名单布尔判定（Rust + 强类型 + 单元测试；不引入 SPARK）
- 资源配额执行器：Rust + TLA+ 建模 + proptest（§4）
- 终止判定：Ada/SPARK C 库（§4），唯一证明组件
- 审计日志：JSON 结构化 + 防篡改；SPARK 不介入（测试保证）

### 5.4 第四层：部署与运维

- Alpine 基础镜像（python3 + sandbox 二进制 + 核心 C 库 + 最小化 libc）< 10MB
- 一次性实例 `--rm`，防代码残留与跨请求干扰；仅 Secure 模式默认路径
- 网络：默认 `--net=none`；`only` 含 net 模块时 `--net=bridge` 限制出站 443/80 + eBPF 流量监控
- 可观测性：容器/审计日志汇总中央日志系统

## 6. 工具链全景

```
1. 编译器（Go）—— 静态安全检查，无需验证
2. 执行模式选择（Rust）—— 动态路由 Fast/Secure
3. 资源记账核心（Rust + TLA+ 建模 + proptest）
4. 终止判定模块（SPARK → C 库）—— 唯一数学证明组件
5. eBPF 网络监控（C + Rust）—— Fast 模式额外审计
```

## 7. 安全保证声明（对外的白皮书表述）

> Fly-lang 沙箱提供两种隔离模式（Fast 进程级 / Secure 容器级），用户可根据安全需求和延迟预算灵活选择。资源记账算法经 TLA+ 建模验证，核心终止判定逻辑经 SPARK 形式化证明，其余组件通过高覆盖率测试与运行时断言保证健壮性。

- **编译时**：覆盖 OWASP Top 10 大部分注入类与配置错误类
- **运行时**：seccomp + 命名空间 OS 级隔离，Python 漏洞无法逃逸进程边界
- **形式化**：终止判定模块数学级正确性；资源记账并发一致性经模型检查
- **审计**：每年一次第三方代码审计，重点审查 Rust 代理与 Ada 模块 FFI 边界
